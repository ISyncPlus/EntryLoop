# Threat model · Phase 2A

## Assets and boundaries

Assets: organizer private signing capability, attendee names/emails, event verification keys, issued-ticket registry, immutable admissions and reliable conflict evidence. Untrusted inputs: CSV/files, QR pixels/text, claimed event packages/scanner IDs, clocks and same-origin browser state under a compromised device. No backend, user login or authenticated staff directory exists.

| Threat                                    | Implemented handling                                                                                              | Remaining limit                                                                                                                                                              |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Forged or modified ticket                 | Strict token schema, expected event, ECDSA P-256/SHA-256 verification, issued-ID membership                       | Authenticity is relative to the correctly pinned organizer key, not the human presenter                                                                                      |
| Copied valid ticket                       | Known local admission rejected transactionally; disconnected duplicates preserved as conflicts                    | Cannot stop simultaneous admissions on disconnected devices; no photo/identity check or revocation                                                                           |
| Malicious initial event package           | Size/schema/signature checks plus mandatory full fingerprint confirmation obtained independently                  | Included key/self-signature cannot identify organizer; operator can trust the wrong fingerprint                                                                              |
| Key substitution or package rollback      | Existing key pinned, revisions monotonic, equal-revision conflicts rejected                                       | No authorized key rotation/recovery flow                                                                                                                                     |
| Private signing key leakage in exports    | Non-exportable native CryptoKey; explicit public-only package/token fields; strict unknown-field rejection        | Same-origin malicious code can still invoke signing; non-exportable does not defeat XSS/compromised devices                                                                  |
| Guest-list leakage to scanners/sync       | Names/emails remain organizer-only; opaque IDs in ticket QR, catalog and sync                                     | Ticket SVG/HTML files include names; pseudonymous IDs can still be correlated. Profiles are not access control                                                               |
| Roster tampering/duplicates               | Bounded strict Zod input, validated CSV preview, normalized unique emails, atomic writes                          | No roster encryption, shared-email exception, attendee edit/deletion or organizational access controls                                                                       |
| Stale concurrent event edits              | Loaded revision checked inside transaction; explicit draft reload; immutable ID/key and locked name/date/location | Descriptions require re-export for scanner metadata updates; no live remote propagation                                                                                      |
| Forged admission sync batch               | Schema/hash/event/catalog validation, collision rejection and atomic deduplication                                | **Operations remain unsigned. An attacker knowing a valid ticket ID can forge an admission batch and recompute its hash. Ticket signatures do not authenticate operations.** |
| Missing/replayed QR batches               | Operation-ID deduplication; all distinct admissions preserved                                                     | No delivery acknowledgment, peer inventory or automatic completeness proof                                                                                                   |
| Operation ID reused with changed contents | Entire batch rejected; existing evidence retained                                                                 | No forensic quarantine UI for rejected payloads                                                                                                                              |
| Browser clearing, eviction or device loss | IndexedDB persistence and restart tests; UI warns about local storage                                             | No backup/key recovery; key loss can permanently stop issuance for the event                                                                                                 |
| Hostile image/export content              | Local image MIME/10 MiB bound; escaped SVG/HTML text; no payload HTML injection or image upload                   | No comprehensive image decompression-bomb defense or third-party dependency security audit                                                                                   |
| Clock manipulation                        | Time is metadata only; no identity/winner based on clock                                                          | Event dates are descriptive, not enforced expiration/admission windows                                                                                                       |
| Origin/transport attacks                  | Camera/WebCrypto/service worker require HTTPS or localhost; optional user-managed local TLS                       | No deployment/security-header review; same-origin compromise or malicious extensions can alter data                                                                          |
| Large event/workload                      | 5,000 attendees, 1 MiB CSV/package, 512-byte ticket, 5-record/900-byte sync bounds                                | Large-event runtime, storage quotas and aggregate-log growth are not load-tested; HTML ticket sheets cap at 500                                                              |

## Cryptographic scope

Use native ECDSA P-256 with SHA-256 and raw r||s signatures. Tickets sign only canonical event/ticket IDs under a ticket-specific domain. Packages sign canonical metadata/key/catalog under a separate domain. Verification information does not include private keys. Public-key fingerprints are the initial human trust anchor; a self-signed package is not third-party identity certification.

Cryptographic primitives/serialization have native Node, Chromium and WebKit automated coverage. This is not a cryptographic implementation audit or a claim of end-to-end staff authorization. Production-safe synchronization still needs authenticated staff devices and signed operation evidence, as well as revocation, recovery, privacy and conflict-handling policies.

## Hardware evidence

The owner reports successful Phase 1 physical QR reconciliation with identical logs and the expected conflict. New Phase 2A ticket signatures, provisioning, mobile camera ergonomics and install behavior were not tested on physical devices in this session. Browser/image tests are labeled as such.
